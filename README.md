# Customer Lifetime Value for Primark (synthetic data)

An end-to-end, offline demo that predicts what each customer will be worth over the next 6 and 12 months, finds the high-value customers who are quietly drifting away, and recommends what to do about each group.

> **All data in this project is synthetic.** It is generated by code in this repository, modelled on Primark-style UK and Ireland shopping behaviour. It contains no real customers and no real Primark data. Campaign save rates, campaign costs and loyalty effects are illustrative assumptions, labelled as such in the app.

**Team:** Rapid Builders. **Opening film:** [media/C10000_story.mp4](media/C10000_story.mp4) (45 seconds, with a silent backup alongside it).

---

## 1. The business question

Primark has many customers it can identify through the loyalty and app programme, and little visibility of which ones are about to stop shopping. This project answers three questions for a board audience:

| Question | Where it is answered |
|---|---|
| How much is each customer worth over the next 6 and 12 months, and how much of that is at risk? | Overview, Customers |
| Who should we act on first, and what should we do? | Segments, Customers |
| What would a bigger loyalty programme be worth? | Loyalty |

## 2. Quick start (Windows, VS Code, offline)

Prerequisite: Python 3.12 (3.10 to 3.12 all work).

```powershell
# 1. open the folder in VS Code, then open a terminal (Ctrl+`)
python -m venv .venv
.venv\Scripts\Activate.ps1          # if blocked: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
pip install -r requirements.txt

# 2. build everything (about a minute): data, features, models, segments, loyalty
python run_all.py

# 3. start the app
uvicorn api.main:app --reload
```

Open **http://127.0.0.1:8000**. The interactive API test page is at **http://127.0.0.1:8000/docs**.

Handy variations:

| Command | What it does |
|---|---|
| `python run_all.py --skip-data` | Re-runs models, segments and loyalty on the existing synthetic data |
| `python check.py` | Confirms the Python environment is ready |
| `python -m src.models` | Re-runs just one stage (every stage in `src/` can run alone) |

Nothing needs the internet once the packages are installed.

## 3. How the repository works

### 3.1 The big picture

```mermaid
flowchart LR
    A[1. generate_data<br/>synthetic world] --> B[2. features<br/>one row per customer]
    B --> C[3. models<br/>churn and CLV]
    C --> D[4. segments<br/>who and what to do]
    C --> E[5. loyalty<br/>value of the programme]
    D --> F[(outputs/<br/>parquet and json)]
    E --> F
    C --> F
    F --> G[api/service.py<br/>loads everything once]
    G --> H[api/main.py<br/>FastAPI routes]
    H --> I[web/<br/>five-page front end]
```

Plain-text version of the same flow, in case your viewer does not draw diagrams:

```
 src/generate_data.py  ->  data/primark_clv.db           (5 tables, 20,000 customers)
 src/features.py       ->  outputs/features_*.parquet    (one row per customer, 3 snapshots)
 src/models.py         ->  outputs/predictions_*.parquet, metrics.json, models/
 src/segments.py       ->  outputs/customer_segments.parquet, segment_summary.json
 src/loyalty.py        ->  outputs/loyalty_analysis.json, loyalty_uplift.parquet
 api/service.py        ->  reads outputs/ and the database, answers questions
 api/main.py           ->  HTTP routes (/api/...) and serves web/
 web/                  ->  what the audience sees in the browser
```

**Two rules explain the whole design.**
1. **Everything heavy is computed ahead of time** by `run_all.py`. The app only reads results, so every click in the demo is instant.
2. **Each stage reads the previous stage's files and writes its own.** You can re-run any stage alone, and you can inspect any intermediate file.

### 3.3 Stage 1: the synthetic world (`src/generate_data.py`)

Builds five tables in `data/primark_clv.db` (SQLite) and as CSV copies.

```mermaid
flowchart TD
    S[config.py<br/>seed 42, 20,000 customers,<br/>1 Oct 2023 to 30 Sep 2026] --> G[generate_data.py]
    G --> T1[customers<br/>age, region, join date]
    G --> T2[transactions<br/>one row per category per visit]
    G --> T3[returns<br/>items brought back]
    G --> T4[loyalty<br/>membership and app]
    G --> T5[email_engagement<br/>sent, opened, clicked per month]
    G --> GT[_ground_truth_for_validation.csv<br/>hidden truth, used only to check the model]
```

Each customer has their own visit rate and their own chance of quietly leaving after each visit (the classic BG/NBD story). Visits are more likely at weekends and in busy months. Loyalty members visit slightly more and leave slightly less, which is an assumption stated openly. One hand-crafted customer, **C10000**, is the guided-demo character: a 38-year-old loyal family shopper in Manchester whose gaps between visits stretched from 26 to 31 to 38 to 60 days. A second hand-written customer, **C10001**, is the contrast: a 24-year-old in Leeds with small baskets (about £6 a visit) who shopped every six weeks or so through 2025 and has not been back since Black Friday. She is written in after all random draws, and the models score her but never train on her, so adding her changes no other customer's numbers.

The same seed always produces the same data.

### 3.4 Stage 2: features (`src/features.py`)

Models cannot read thousands of receipts, so each customer's history is summarised into about 50 measures: recency, frequency, tenure, average basket, category shares, return rate, loyalty and app status, email behaviour and more (see the data dictionary on the Model page).

It is built at **three snapshots** so the model is tested on a future it never saw:

```mermaid
timeline
    title Three snapshots, one honest test
    section Past
        30 Sep 2024 (train) : features measured here : what really happened in the next 6 and 12 months is the answer key
        30 Sep 2025 (test) : kept aside : proves the model works on a new year
    section Today
        30 Sep 2026 (score) : features only : this is what the app shows
```

A snapshot only uses information that existed on its date, so nothing from the future leaks in. Spend is counted **net of returns**.

### 3.5 Stage 3: the models (`src/models.py`)

> CLV over the next 6 or 12 months = expected visits x expected spend per visit

```mermaid
flowchart TD
    F[Customer features] --> B[BG/NBD<br/>survival-style visit model]
    F --> G0[Boosting alone<br/>no visit-model signals]
    F --> G1[Gradient boosting<br/>spend per visit]
    B --> P[chance still active<br/>churn risk = 1 minus this]
    B --> V[expected visits<br/>6 and 12 months]
    V --> H[Hybrid CLV<br/>visits x spend per visit]
    G1 --> H
    F --> G2[Stacked gradient boosting<br/>predicts spend directly,<br/>also sees BG/NBD signals]
    P --> G2
    V --> G2
    H --> FIN[Final CLV<br/>average of hybrid and stacked]
    G2 --> FIN
    FIN --> OUT[CLV 6m and 12m,<br/>potential CLV if kept active,<br/>revenue at risk]
    BASE[Baseline<br/>keep spending what they spent before] -.compared against.-> FIN
    RFM[RFM benchmark<br/>average by recency, frequency, spend band] -.compared against.-> FIN
    G0 -.compared against.-> FIN
```

- **BG/NBD** uses three numbers per customer (repeat visits, time of last visit, customer age) to estimate the chance they are still active and how many visits to expect. We use a small variant that lets a customer leave right after the first visit, because that is common in retail.
- **Gradient boosting** (LightGBM, with a scikit-learn fallback if LightGBM is not installed) learns spend per visit from basket size, categories, returns, loyalty and email behaviour.
- **Final CLV** averages two views (hybrid and stacked) because that blend gives the smallest error in the *total* forecast, not because it wins on every customer.
- **Potential CLV** is the value if the customer stays active. **Revenue at risk = potential CLV x churn risk.**

**The scorecard is a ladder.** Each row adds one idea, so you can see what each one buys. The Model page shows the same table.

| Row | What it is | Reference run, 12 months: average miss, total vs actual |
|---|---|---|
| Baseline | Keep spending as before | £86.94, +168% |
| RFM benchmark | Average by recency, frequency and spend band (5x5x5 bands, edges set on training data only) | £41.72, +4.2% |
| Boosting alone | Gradient boosting with no visit model | £37.24, -9.0% |
| Visit model alone | BG/NBD visits x past basket | £40.55, +11.1% |
| Hybrid | Visit model x boosting basket | £39.29, +11.7% |
| Stacked | Boosting that also sees the visit-model signals | £36.72, -9.7% |
| **Final** | Blend of hybrid and stacked | **£37.73, +1.0%** |

**What the ladder says, honestly.**
- The final model is about 10% better than the standard RFM method on average miss. The naive baseline is a weak yardstick, so RFM is the fair comparison.
- Most of the accuracy comes from the customer facts fed to boosting. Boosting alone is within about £0.50 of the final on average miss.
- The visit model earns its place elsewhere: it gives a *churn probability* (detection score about 0.85, against 0.83 from recency alone) and splits value into expected and at risk. Boosting alone cannot do that.
- Boosting alone and stacked under-forecast the total by about 9 to 10%, while the blend lands within about 1%. That is why the final is a blend.

Your numbers will differ slightly with the model engine used.

Because the data is synthetic, the generator's hidden true settings are known, and the Model page shows that the BG/NBD parameters the model learned land close to them.

### 3.6 Stage 4: segments (`src/segments.py`)

```mermaid
quadrantChart
    title Two questions place every customer
    x-axis Low churn risk --> High churn risk
    y-axis Lower value --> Higher value
    quadrant-1 Protect
    quadrant-2 Grow
    quadrant-3 Maintain
    quadrant-4 Win back
```

| Segment | Meaning | Play |
|---|---|---|
| **Protect** | High value, likely to be slipping away | Personal outreach before they lapse |
| **Grow** | High value, still active | Reward and deepen, no discounts |
| **Win back** | Lower value, likely gone | Low-cost reactivation, email first |
| **Maintain** | Lower value, still active | Keep warm, no extra spend |

High value means the top 30% of customers by potential 12-month CLV. High risk means a churn risk of 50% or more. For every customer the stage writes plain-English reasons ("last visit 102 days ago, 5.1 times their usual gap") and a suggested next action. For each segment it estimates what a campaign could recover, using **illustrative** save rates and costs defined at the top of `segments.py` (currently Protect 20%, Win back 12%, Grow upside 5%). Replace them with Primark's real response and cost data before using the numbers for decisions.

### 3.7 Stage 5: loyalty value (`src/loyalty.py`)

```mermaid
flowchart LR
    M[Members] --> FM[Fit BG/NBD<br/>separately]
    N[Non-members] --> FN[Fit BG/NBD<br/>separately]
    FM --> R[Visit-rate and leave-rate ratios<br/>members vs non-members]
    FN --> R
    R --> U[For every non-member:<br/>CLV if they behaved like a member<br/>minus CLV today]
    U --> C[Uplift curve:<br/>enrol best prospects first<br/>or at random]
    C --> S[Simulator<br/>enrolment %, share caused by the programme,<br/>cost per enrolment]
```

**Honesty note.** Members and non-members differ in other ways too, because keener shoppers are more likely to join. The result is an **association, not proof of cause**. The simulator therefore lets the audience choose how much of the gap they believe the programme really causes (default 50%).

```mermaid

```

| Route | Used by |
|---|---|
| `GET /api/overview` | Overview page |
| `GET /api/segments` | Segments page |
| `GET /api/customers`, `GET /api/customers/{id}` | Customers page and segment lists |
| `GET /api/demo` | The guided-demo customer, C10000 |

| `GET /api/model` | Model page |

`main.py` contains only routes, plus one small rule: page files (HTML, CSS, JavaScript) are sent with `Cache-Control: no-cache`, so the browser always checks for a newer version and code updates show up without a hard refresh. All logic is in `service.py`, so it can be tested without a web server.

Each customer response also carries `campaign` (expected money back, expected cost and net, from the same assumptions as the Segments page) and the customer's `city`.

### 3.9 The front end (`web/`)

No framework and no build step: plain ES modules that the browser loads straight from the server.

```mermaid
flowchart TD
    H[index.html<br/>top bar, theme switch] --> A[app.js<br/>hash router]
    A -->|#/overview| P1[pages/overview.js]
    A -->|#/segments| P2[pages/segments.js]
    A -->|#/customer| P3[pages/customer.js]
    A -->|#/loyalty| P4[pages/loyalty.js]
    A -->|#/model| P5[pages/model.js]
    P1 & P2 & P3 & P4 & P5 --> API[api.js<br/>fetch and cache]
    P1 & P2 & P3 & P4 & P5 --> CH[charts.js<br/>hand-written SVG]
    P1 & P2 & P3 & P4 & P5 --> U[util.js<br/>formatters]
    CSS[css/app.css<br/>tokens for light and dark] -.styles.-> H
```

- **Theme:** white by default, dark on the switch. All colours are CSS variables under `:root[data-theme]`, so charts follow the theme without redrawing. The choice is remembered in the browser.
- **Charts:** hand-written SVG (no chart library), so the demo works with the network off.
- **Colours:** segment colours are fixed (Protect orange, Grow green, Win back blue, Maintain grey) and were checked for colour-blind separation in both themes.
- **Overview sliders:** the hero has two save-rate sliders (Protect 0 to 60%, Win back 0 to 40%). Dragging them recalculates the recoverable figure and the net return after campaign cost, in the browser, from the same assumptions the Segments page shows.
- **Customers page:** tells one customer's story in five steps, context first and conclusion last:
  1. **Who she is:** a tenure ring (a full circle is 3 years), one sentence about her ("38, Manchester. A loyal family shopper. Mostly Womenswear, about every 20 days."), four facts (visits, total spend, typical basket, returns) and three tiles showing how we can reach her (loyalty, app, email). Email opens turn orange only when they are falling.
  2. **How she shops:** days between visits, what she buys, her last visits.
  3. **What the model sees:** chance she is still active over time, and the five key numbers.
  4. **What we do about it:** segment, rank, reasons and the recommended next step.
  5. **Compared with another drifting customer:** C10000 and C10001 side by side (shown for the two demo customers).

  Every number comes from the customer's own profile. The only hand-written words are the short labels for the two demo customers ("A loyal family shopper", "An occasional shopper").
- **Model page:** shows the full scorecard ladder with a plain-English note on what boosting alone achieves and what the visit model adds.
- **Motion:** one entrance animation and the lines that connect the Overview bar to the segment tiles. Both respect the reduced-motion setting.

## 5. Why there is no LLM in the engine

This is a deliberate design choice, not a gap.

- **The question is about numbers.** Forecasting spend and churn from transaction history is what statistical and machine-learning models are built for. Language models are built for words.
- **Same input, same answer.** Every number is reproducible, traceable to a customer's history, and tested on a year the model never saw. An LLM's answer can vary from run to run and cannot be backtested the same way.
- **Customer data stays inside.** Nothing is sent to an outside AI service; the whole pipeline runs offline.
- **Cost at scale.** Millions of customers can be scored in minutes with no per-call fees.

Where language AI fits later: on top of the results, never underneath them. For example, a short briefing per customer for the CRM team and a draft message in Primark's voice, with a person approving every message and the model never calculating anything.

## 6. Limits worth stating out loud

- The data is synthetic. Real Primark data would need the same five tables, and real behaviour will not match a simulation exactly.
- Only customers identified through the loyalty programme, app or email are visible. In-store shoppers who are never identified are not in the data.
- Campaign effects, costs and the loyalty causal share are assumptions, not measurements. They should be replaced with Primark's own test results.
- BG/NBD assumes purchase behaviour is steady over time. It does not model one-off events such as a store closure or a major promotion.
- The accuracy test is partly circular: the data was generated by a process similar to what the visit model assumes. The honest proof is a pilot on real data.
- Gender and age are currently model inputs. They are sensitive attributes and should be removed or reviewed before real use.
- There is no uncertainty range on a prediction and no per-customer list of drivers beyond the plain-English reasons. No model version log, CSV export or drift monitoring yet.
- No channel or promotion data is modelled, there is no login, and the demo runs on 20,000 customers rather than a production-scale base.
- Planned but not built: a customer briefing with a draft message, and a campaign design assistant, both using an LLM with an offline fallback. The LLM would never calculate numbers; it would only phrase what the models already produced.

## 7. Troubleshooting

| Symptom | Fix |
|---|---|
| `Activate.ps1 cannot be loaded` | `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`, then activate again |
| `python` not found | Use the full path to `python.exe` to create the venv, then use the venv from then on |
| Page says "Something went wrong loading this page" | The server stopped. Restart `uvicorn api.main:app --reload` |
| Numbers look stale after a model change | Run `python run_all.py --skip-data`, then restart the server |
| Charts or styles look unchanged | Restart the server, then press Ctrl+F5 once. After that, page files are re-checked on every load |
| A huge black circle fills the Customers page | The browser kept an old `app.css`. Same fix: restart the server and press Ctrl+F5 |
| `uvicorn` log shows only `/` and `/api/...`, never `.js` or `.css` | The browser is using saved copies. Open developer tools (F12), tick "Disable cache" on the Network tab, and reload |
| Diagrams show as code in VS Code | Install the extension "Markdown Preview Mermaid Support", or use the plain-text flow in section 3.1 |
